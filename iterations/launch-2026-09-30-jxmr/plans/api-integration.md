# launch-2026-09-30-jxmr — API integration plan (L-60)

**Status: approved (2026-10-09, [D148](decisions.md)); the build is under way.** This is the plan that
replaces every fixture-backed and planned call in the clinic with clinozy-be's built API, and removes
the design features the backend dropped. It was written before any code, as asked. The five questions
the foundation needed are answered (§10); the rest are asked as each screen comes up.

## 1. What the research found

1. **Every design operation has a route.** What is missing is mostly display data (joins, counts,
   flags) and a few writes (Undo of some moves, a few filters); [§8](#8-gaps--what-a-screen-needs-and-the-api-does-not-have)
   lists each.
2. **Four blockers** decide how far some screens can go:
   - **B1 — files cannot be read back (N4).** No route or field turns a `file_key` into a URL
     (`GET /uploads/:upload_id` is metadata only; the only download URLs in the document are the
     GDPR export's). Photo thumbnails and the viewer, report downloads, review files and message
     attachments cannot render.
   - **B2 — the caller's own membership id (N10).** `GET /auth/me/context` has `my_role_ids` and
     `my_permissions` but no `membership_id`; every "Mine", "(you)" and owner filter needs it.
   - **B3 — nothing to verify against.** Demo Organization has no clinic data and only the Admin
     role (the eight role presets apply only at provisioning).
   - **B4 — the OpenAPI document's gaps** limit generated types: no response field is marked
     required, four responses are untyped, DELETE's `reason` / `note` and the error `reason` are
     undocumented (§9 M2–M5).
3. **Calls that are already real are broken against the built API** (Settings › Members and the
   Users room): the members list parses every row as invalid, invite / role / status writes get
   `400`, the invitation resend / revoke / accept paths `404`, and `core/types/permissions.ts`
   still names `membership:manage`, `invitation:manage`, `role:manage`, which no longer exist.
4. **Billing does not apply offers.** An invoice line's rate is `offer_price ?? price`
   (`invoices.lines.ts:200`); live offers (percent, amount, fixed, extra sessions) never reach an
   invoice, though routes-final §3.10 says "billing applies the same rule" (M26, Q6).

## 4. Conventions at the API boundary

- **Where things convert.** Only in each room's `<domain>-contracts.ts` wire schema and its mapper
  (backend-handoff step 2): snake_case → the domain's camelCase, public ids, rupees, `*_number`,
  enum values. Screens read the domain contracts and never see the wire.
- **Enums.** The API's values replace the design's wherever they differ (each room's table names
  them); labels stay in the locales.
- **Server-computed values** are read, never derived: invoice amounts, GST, due and paid, payment
  status, slots, the patient's ideas, stock balance and level, an offer's status, the day close's
  expected cash, a supplier's payable (§7).
- **Writes** carry F5's key on the routes marked **req**, `expected_updated_at` on PATCH (F7),
  and a delete reason (F9).
